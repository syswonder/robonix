# Robonix\-ScribeMem

## Scribe Mem 设计动机 \- Motivation

具身记忆的需求可以从三个层次理解，每一层解决一类 LLM 自身无法覆盖的问题：

**第一层：核心需求 — 记住发生过什么**

LLM 的上下文窗口有硬上限，且每次会话独立。机器人执行一个长程任务可能跨越数十轮交互——每一轮的场景描述、动作记录、执行结果。如果不加记忆，LLM 在第 10 轮时已经"忘记"了第 1 轮做了什么。核心需求是：

|需求|说明|没有记忆的后果|
|---|---|---|
|跨轮次上下文保持|长程任务跨越数十轮交互，每轮的场景\+动作\+结果需要持久化|LLM 只能在当前窗口中推理，丢失历史信息|
|多模态统一存储|视觉\(VLM描述\)、空间\(坐标\)、行为\(动作序列\)、语言\(指令\)需统一索引|各模态信息散落在不同模块，无法联合检索|
|空间\-语义绑定|"厨房"不只是文本 token，还关联具体的 3D 坐标和物体列表|无法回答"厨房在哪""厨房里有什么"|
|成功/失败标记|每次执行的结果必须与场景上下文绑定存储|无法从历史中区分"哪些做法可行、哪些不行"|

**第二层：历史任务的检索 — 找到相关的过去**

记住只是第一步。当用户说"把红杯子拿过来"，机器人的记忆库里有 5000 条记录——其中只有 2 条与当前任务相关。检索需求不是简单的"语义相似"，而是多维度约束下的精确召回：

|检索维度|示例查询|检索约束|
|---|---|---|
|**语义匹配**|"抓取杯子的经验"|向量相似度：查询文本 vs 记忆 summary|
|**空间过滤**|"厨房里的"|`scene_type=kitchen` — 排除客厅/卧室的相似经验|
|**行为过滤**|"抓取"而非"放置"|`action_type=grasp` — 排除无关动作类型|
|**结果过滤**|"成功的"|`success=true` — 排除失败经验（除非主动检索教训）|
|**时间过滤**|"最近一周的"|`timestamp` 范围 — 排除过期经验|
|**可执行性过滤**|"我当前能做到的"|机器人能力匹配 \+ 前置条件检查 — 排除"需要双臂但我只有单臂"的经验|

```Plaintext
检索的精度要求：
  "5000 条记忆中，找到在厨房成功抓取红杯子的那一条"

  纯语义检索：Top-5 可能包含"厨房抓杯子""客厅抓杯子""厨房抓盘子"...
              → 语义都相似，但只有 1 条在物理空间上可用

  标签+向量检索：kitchen ∩ grasp ∩ cup ∩ success → 候选 2 条
              → 在 2 条上做向量精排 → 1 条精确命中
```

**第三层：技能的提炼生成 — 从经验到能力**

记住 100 次"采集木头→制作木板"的经验，不等于"会做木板"。真正的能力是：下次用户说"做木板"，不需要重新检索 5 条经验再让 LLM 推导步骤，而是直接调用 `craft_plank` 技能。

技能提炼需求解决的是从"经验记忆"到"程序性知识"的跃迁：

|阶段|输入|输出|LLM 的工作量|
|---|---|---|---|
|**无记忆**|仅当前场景|LLM 从零推导完整动作序列|最高（每次都是第一次）|
|**有记忆无提炼**|当前场景 \+ Top\-5 相关经验|LLM 阅读经验 → 提取公共模式 → 推导步骤|中等（需要从经验中归纳）|
|**有提炼技能**|当前场景 \+ 可用 Skill 列表|LLM 直接调用 `craft_plank` tool|最低（1次 tool call）|

提炼的产出不是"一段文字"，而是一个**可执行、可验证、可版本管理**的 Skill 模板：

```Plaintext
Skill: "craft_plank"
  ├── 前置条件: 需要 log（必须）+ crafting_table（可选, p=0.67）
  ├── 动作序列: locate→collect→craft（3步因果链）
  ├── 后置条件: plank+4, log-1
  └── 成功率: 0.95（基于 20 次历史执行）
```

这个 Skill 可以被 Pilot 注册为 MCP function tool，LLM 在规划时直接看到它是一个可调用工具，不再需要从零推导制作链。

**三层需求的递进关系**：

```Plaintext
记住（核心）        检索（历史任务的查找）      提炼（技能生成）
═══════════        ═══════════════════      ═══════════════

经验→存储为节点      从节点库中精确召回         从相似节点中抽象模式

"发生了什么"         "找到相关的过去"          "把经验变成能力"

                   ┌─────────────────────────────────────┐
                   │ 每一层都建立在下一层之上              │
                   │ 检索依赖记住（没有节点就没得查）       │
                   │ 提炼依赖检索（找不到相似经验就没法抽象）│
                   └─────────────────────────────────────┘
```

### 为什么不直接复用 Agent 中的记忆设计？

通用 LLM Agent（MemGPT、LangChain、AutoGPT）的记忆面向的是**纯文本对话**场景，而具身智能面临本质不同的约束：

|约束|Agent 的记忆|具身智能需要什么|
|---|---|---|
|**模态**|仅文本|视觉（RGB/深度） \+ 空间（坐标） \+ 动作（轨迹） \+ 语言（指令）多模态统一|
|**空间**|无|物体在物理世界中的位置 \(x, y, z\)，"厨房"不只是语义标签，还有 3D 坐标|
|**时间因果**|对话顺序即可|动作之间的因果依赖（先采集才能制作），只靠对话顺序不够|
|**可执行性**|文本输出即"执行"|检索到的记忆必须能在**当前机器人**上执行（能力边界、环境约束）|
|**遗忘**|大多只截断不遗忘|需要主动分级遗忘：降权→归档→删除，防止检索退化|
|**任务并行**|不存在|子任务可以双臂/多机器人并行，需要依赖分析|
|**技能积累**|无|从重复成功经验中提炼为可复用的 Skill，注册为 LLM 的 function tool|

1. 多模态 vs 统一表征：视觉/语言/动作需要统一检索，但模态间语义鸿沟大

2. 泛化性 vs 可执行性：语义上相关的记忆不一定可执行（环境/能力约束不同）

3. 任务并行性 vs 线性规划：LLM 天然倾向生成线性的步骤序列，但具身任务中存在大量可并行的子任务（如双手操作、多地点独立采集）。记忆系统需要识别并释放这些并行度，将线性计划重构为并行执行图

### 与语义地图的区别？

语义地图（Semantic Map）是 SLAM 社区的概念扩展，核心思想是**在地理空间上附加语义标签**

|维度|语义地图|M4EI 具身记忆|
|---|---|---|
|**主索引**|空间坐标 \(x, y, z\)|多键索引：语义键 \+ 因果键|
|**信息粒度**|物体级（"这里有椅子"）|事件级（"我在这里抓取椅子失败了"）|
|**时间维度**|通常是静态快照|结构化知识|
|**可执行性**|不包含动作信息|包含完整的动作序列和前置/后置条件|
|**查询方向**|"在哪里？"|"怎么做？""为什么？""上次呢？"|
|**遗忘机制**|通常无（或简单超时）|分级遗忘 \+ 提炼|
|**与其他模态的关系**|视觉语义为主|感知 \+ 行为 \+ 认知三维融合|
|**典型输出**|位置坐标、物体列表|可执行计划、技能模板、安全约束|

语义地图回答"**在哪里**"，具身记忆回答"**怎么做**"和"**发生过什么**"。两者可以联合工作——语义地图提供空间索引，记忆提供行为索引。

### LLM Agent

#### Agent 中的记忆设计

|方案|记忆模型|核心机制|对具身场景的不足|
|---|---|---|---|
|**MemGPT** \(Letta\)|虚拟上下文管理：将 LLM 上下文视为"虚拟内存"，通过自主的"内存分页"在对话中换入换出|LLM 自主决定何时将信息从上下文写入外部存储、何时检索回上下文|仅处理纯文本对话，无空间/多模态概念；无因果链；无提炼→技能的能力|
|**LangChain Memory**|多种 Memory 后端：ConversationBuffer / Summary / VectorStore 等|对话历史→摘要→向量存储→检索增强|面向对话场景，缺省无区分短期/长期/技能分层；遗忘仅基于 token 截断|
|**AutoGPT / BabyAGI**|任务队列 \+ 文件存储|任务分解→执行→结果写入文件→下一轮读取文件作为上下文|文件存储无结构化检索；无标签索引；无因果过滤|
|**Claude Code Memory**|持久化文件记忆 \(`memory/` 目录\)|用户手动 `@remember` 或 AI 自动保存→以 Markdown 文件存储→会话开始时加载索引|面向代码开发场景，无多模态；无需空间坐标；无并行执行概念|

**通用 Agent 记忆的共同局限**：

- **单模态**：仅处理文本，无法利用空间坐标、物体检测结果

- **无因果链**：存储的是"事实"而非"事件序列"，无法回答"为什么失败"

- **无执行闭环**：记忆与动作执行脱节，无法验证记忆中的方案在当下是否可执行

- **无遗忘/提炼**：记忆只增不减，最终检索退化

#### **大模型数据飞轮：记忆作为闭环枢纽**

具身智能的竞争本质是**数据飞轮的战争**。行业方案（高德 ABot、它石智航、原力灵机等）的共识架构是三层飞轮：**数据层 → 模型层 → 应用层 → 回哺数据层**。记忆系统是飞轮中连接原始数据与可执行能力的关键枢纽。



**飞轮在 Scribe Mem 中的映射**：



```Plain Text
执行采集(remember) → 记忆写入(CKG+标签+向量) → 检索增强(search→LLM prompt)
       ↑                                                  │
       │                                                  ▼
       └────────── 更优执行(tool call) ←──── 技能提炼(refine→MCP注册)
```



|飞轮阶段|Scribe Mem|核心机制|
|---|---|---|
|执行→写入|remember|多模态采集、标签先行入 Redis、嵌入入 FAISS|
|检索增强|search|标签 O\(1\)过滤→向量精排→因果过滤、教训注入 prompt|
|技能提炼|refine \+ list\_skills|聚类→抽象→验证→MCP tool 注册、成功率追踪|
|废弃代谢|forget|ForgetRisk 分级遗忘，防止旧数据污染检索质量|



**架构特点**：

\- **失败自动回流**：失败经验标记为"教训"节点，受遗忘保护，支持主动检索和聚合分析

\- **技能原子化**：N 次成功经验提炼为带版本管理的可执行 Skill 模板

\- **遗忘作为代谢**：分级降权/归档/删除，确保飞轮不被过期低质数据污染



**与通用数据飞轮的关键差异**：



|维度|通用数据飞轮|Scribe Mem 的飞轮|
|---|---|---|
|数据流向|数据→模型训练→部署→再采集|执行→记忆节点→检索→提炼→更优执行（在线闭环，无需离线训练）|
|反馈周期|天/周级（依赖模型重训）|秒级（检索注入 prompt）/ 分钟级（提炼 Skill→MCP 注册）|
|产物|更新后的模型权重|结构化记忆节点 \+ 可执行 Skill 模板|
|数据价值利用|主要用成功样本|失败教训同等重要（教训保护\+主动检索）|
|数据质量管理|依赖人工清洗|ForgetRisk 自动评分\+分级处理|

#### Rosclaw

https://github\.com/ros\-claw/rosclaw \- 数据飞轮

rosclaw 是 OpenClaw AI Agent 网关与 ROS2 之间的桥接插件，其记忆系统由 OpenClaw 侧负责，通过 MCP 协议与 ROS2 机器人能力对接。

**架构概览**：



```Plain Text
User (Messaging App / Voice)
        │
        ▼
┌──────────────────────────┐
│  OpenClaw Gateway         │
│  ┌──────────────────────┐ │
│  │ AI Agent + Memory     │ │  ← 记忆在此层
│  │ (12-layer memory)    │ │
│  └──────────┬───────────┘ │
│             │              │
│  ┌──────────▼───────────┐ │
│  │ RosClaw Plugin        │ │  ← ROS2 桥接
│  │ (MCP tools for ROS2) │ │
│  └──────────┬───────────┘ │
└─────────────┼──────────────┘
              │ rosbridge (WebSocket)
              ▼
┌──────────────────────────┐
│  ROS2 DDS                 │
│  Nav2 / MoveIt2 / sensors │
└──────────────────────────┘
```

**12 层记忆架构**：

|层|系统|用途|访问延迟|
|---|---|---|---|
|0|LCM \(lossless\-claw\)|会话内无损上下文：消息 DAG \+ 全文搜索|运行时|
|1|常驻文件|MEMORY\.md / USER\.md / SOUL\.md — 身份\+工作记忆|0ms|
|2|MEMORY\.md|精选长期记忆|0ms|
|3|PROJECT\.md|项目级知识库|0ms|
|4|facts\.db<br>|结构化实体/键值查找 \(SQLite FTS5\)|\<1ms|
|5|Continuity archive|跨会话语义回忆（向量嵌入）|7ms|
|6|Daily logs|原始会话历史 \(memory/\\\*\.md\)|按需|
|7\-9|Runtime plugins|Continuity / Stability / Metabolism|运行时|



**\*\*统一检索 \`memory\_search\`\*\***：一次查询并行命中 4 个后端（continuity 语义向量 \+ facts 结构化查找 \+ files 文档搜索 \+ lcm 全文搜索），返回合并排序结果。

**元认知管线 \(Metacognitive Pipeline\)**：

```Plain Text
对话 → Metabolism (提取事实+知识缺口, ~5min)
          │              │
          ▼              ▼
      facts.db    pending-gaps.json
  (待验证/过期标记)         │
                           ▼
                    Contemplation (3-pass 反思)
                           │
                           ▼
                    Growth Vectors (19 active)
                           │
                           ▼
                    Crystallization (30+ 天后固化)
```

**MCP 与 ROS2 的桥接方式**：rosclaw 将 ROS2 的能力（topic publish、service call、action goal）封装为 MCP tools，Agent 通过 \`memory\_search\` 检索上下文后，调用对应 MCP tool 执行机器人操作。每个机器人注册自己的 capability profile，Agent 据此判定可执行哪些动作。

**关键设计原则**：

\- **分层检索**：结构化查 facts、语义查 conversations、全文查 commands — 不同类型用不同层

\- **会话内无损 \+ 跨会话语义**：LCM DAG 保证会话内不丢信息，Continuity 保证跨会话能找回

\- **MCP 标准化接口**：Agent 与机器人的唯一桥梁，解耦认知层与执行层

\- **文件自举**：Agent 每次启动从 MEMORY\.md 等文件重建状态，无隐藏状态

\- **Hebbian 激活衰减**：被访问的事实保持"热"态，未使用的逐渐冷却

**与 Scribe Mem 的差异**：

|维度|rosclaw \(OpenClaw\)|Scribe Mem \(Robonix\)|
|---|---|---|
|记忆定位|Agent 内置（网关层）|OS 级独立 service|
|消费者|仅 Agent 自身|Pilot / Executor / Dashboard 多模块共享|
|多模态|文本为主|视觉\+空间\+动作\+语言统一索引|
|空间感知|无，机器人坐标不参与检索|空间标签\+坐标，区分物理位置|
|技能提炼|无，元认知管线提炼的是"事实"|从 N 次成功经验提炼可执行 Skill，注册为 MCP tool|
|遗忘|衰减制（cooling）|分级遗忘（降权→归档→删除）\+ 保护规则|
|可执行性过滤|MCP capability profile 匹配|因果键过滤：前置条件\+能力\+环境三重检查|

#### Skill\-3D

https://zhuanlan\.zhihu\.com/p/2047369078164172865

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NWRjNzU1MmQ4MTY0NDdiZDIxNWVjN2UwOGZiMWVjNzVfZjE2MDZjMjMzZTJhNmY3ZmQ2MGYxMDQwNmZiMDVjOGJfSUQ6NzY1MzMwNzkwNDA0MDIwOTYwOV8xNzgyMTE0Nzg1OjE3ODIyMDExODVfVjM)

**阶段一：场景感知技能提取——"好记性不如烂笔头"**

这是Skill\-3D最精妙的设计。当Agent在某个场景下执行工具调用时，系统会完整记录整个过程，包括：

- 场景类型（如"浴室度量距离"、"客厅物体计数"）

- 工具调用序列（先调了什么、后调了什么）

- 工具返回结果

- 最终答案是否正确

所有这些记录被存入一个叫场景记忆（Scene Memory）的数据库。听起来像日志系统？不止——Skill\-3D在此基础上做了一个关键操作：从场景记忆中蒸馏技能。

**阶段二：技能引导推理——"对号入座选工具"**

到了推理阶段，流程就清晰多了：

1. 场景理解：Agent先分析当前问题——这是什么场景类型？需要什么证据？单视角还是多视角？

2. 技能检索：从技能库中检索与当前场景最匹配的动态技能；如果没有，退而求其次使用静态种子技能

3. 工具规划：根据技能指导，生成最小但充分的工具调用序列

4. 证据收集：执行工具调用，严格基于工具返回的证据进行推理

5. 答案生成：整合多源证据，给出最终答案

**阶段三：Agent式后训练——"把小模型也教会"**

Skill\-3D还有一个野心更大的设计：把这些技能指导下的行为模式迁移到更小的模型中。

作者采用了"技能引导的Agent后训练"——用技能引导的优质轨迹作为训练数据，先进行Agent SFT（监督微调），再用[GRPO](https://zhida.zhihu.com/search?content_id=276486201&content_type=Article&match_order=1&q=GRPO&zhida_source=entity)（Group Relative Policy Optimization）进行强化学习。

## Scribe Mem 设计

```Plaintext
通用 Agent 记忆           具身 Agent 记忆           Robonix Memory
══════════════           ══════════════           ════════════════
                         
文本对话 ──→ 记忆         多模态 ──→ 记忆           多模态 ──→ 标签+向量+因果 ──→ 记忆
   │                        │                          │
   │                        │                          ├── 提炼 Mem → 技能
   │                        │                          │
   └── 纯语义检索             └── 语义+空间检索           ├── 遗忘 → 分级降权
                                                        │
                                                        └── OS 服务化 → 多模块共享
```

Robonix Memory 的核心定位不是"更好的 RAG"，而是**从经验到技能的完整生命周期管理**——记住发生了什么、找到相关的、抽象出模式、清理无用的、在执行前校验安全性。这五个环节缺一不可，共同构成具身智能从"每次从零推理"走向"越用越聪明"的基础设施。

### Scribe Memory 的设计取舍

综合以上方案的优势与不足，Robonix Memory 做了以下关键取舍：

|设计点|借鉴来源|Robonix 的改进|
|---|---|---|
|**分层记忆**（短期/长期/技能/固定）|M2PA 的三分法 \+ 认知科学模型|增加了技能层（从经验中提炼），且每层有明确的转化规则和遗忘策略|
|**标签\+向量双索引**|Embodied\-RAG 的语义森林 \+ LangChain 的向量检索|标签先行（O\(1\) 倒排交集）→ 向量精排（仅对候选集），避免全量暴搜|
|**因果知识图谱**|STMA 的动态知识图谱|增加了因果边 \+ 因果键过滤（检索后检查可执行性），确保检索到的记忆在当前场景可用|
|**提炼→技能**|—（M4EI 创新）|从 N 个相似成功经验中抽象 Skill 模板，注册为 LLM 的 function tool|
|**分级遗忘**|—（M4EI 创新）|ForgetRisk 评分 → 降权/归档/删除三级处理，防止记忆淹没|
|**OS 级服务化**|Robonix 架构|非内嵌到 Pilot，而是独立 service，Executor/Sentinel 等也可直接调用|
|**多模态输入管道**|DeepEmbody 的模拟集成|标准化为 contract 接口，兼容多种模拟器（Malmo / Genesis / Webots）|

#### Demo 1：物体时空回溯 —— 验证"历史记忆：物体昨天放哪了" \- 基础实现

#### Demo 2：任务历史回溯 —— 验证"历史记忆：之前让你做了什么" \- 基础实现

**验证的能力**：基础实现 —— `remember`（写入）\+ `search`（标签\+向量检索）\+ 空间坐标复用

#### Demo 3：重复任务加速 —— 验证"记住 \+ 检索" \- 核心实现

**场景**：用户连续两天让机器人执行相同的任务。 避免无用的探索

**验证的能力**：基础实现 —— `remember`（写入）\+ `search`（标签\+向量检索）\+ 空间坐标复用

#### Demo 4：从经验中长技能 —— 验证"提炼" \- 核心实现

**场景**：机器人执行了 5 次"倒水"任务（每次环境不同，但步骤相同）。第 5 次后，Memory 自动提炼出 `倒水` 技能。

**验证的能力**：核心实现 —— `refine`（聚类\+抽象\+验证）\+ `list_skills`（技能注册为 MCP tool）

#### Demo 5：记忆库自动清理 —— 验证"遗忘" \- 核心实现

**场景**：机器人运行一个月后积累了 5000 条记忆。遗忘机制自动识别并清理低质、过期记忆。

**验证的能力**：核心实现 —— `forget` 全流程（评分\+分级处理\+审计日志）\+ 保护规则验证（固定/教训/Skill源三类不被遗忘）
